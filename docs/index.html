There is deliberately no “try it live” button: this is a REST API with no UI, no deployed instance, and no cloud account wired to the repository — a stated non-goal, not a gap hidden behind a badge. A fresh clone runs the whole eval suite with zero credentials.

purposeA ranker with two paths, and nothing to buy its way past a filter

A caller searches a catalogue of real-estate listings — free text plus structured filters — and the service returns a ranked result set, combining lexical (BM25-style term overlap) and dense-vector retrieval against a synthetic Swiss catalogue in French, German and English. Full-text search over a document store is a solved problem with a library. What is not solved, and what every hybrid system gets wrong somewhere, is a ranker that combines two retrieval paths without letting either become the hole the other path's guarantees leak through.

A query resolves its hard filters once, then two retrieval stages independently build the filter they pass to the index — deliberately not sharing one mutable object, because that independence is exactly the seam a hybrid system's asymmetric bugs live in. The ranker then reads a listing's own free text for ranking-manipulative language, reports what it found — and never lets that finding touch a score.

run itZero credentials is a designed property, not a temporary state

dotnet run --project src/ListingSearch.AppHost starts the service on the fixture catalogue; dotnet test runs the unit tests, Layer 1, the mutation pass and the judge machinery. No account, no container registry, no cloud subscription, no Elasticsearch cluster. The in-memory fixture index is the default (SearchIndex:Mode=Fixture); Elasticsearch is opt-in for local development only, via docker-compose up — never what the automated suite runs against.

what the suite caughtNumbers first, including the unflattering ones

Two findings to date, and neither was the pipeline behaving unexpectedly under real traffic — there has never been any. F-1: a scenario asserted exact ranks on the unstated assumption that only two candidates would score above zero; running the harness against the real pipeline surfaced a third, and the fix was the assertion, not the code. F-2: an early design would have put a second, independent filter check inside the index decorator — reasoning through what the mutation pass would need to prove showed that this made the intended defect structurally uncatchable, before any mutation code existed. Full write-up, including what the suite has not caught, in docs/FINDINGS.md.

one request, end to endThe filter is enforced once, independently, by each path

One service handles everything a caller touches. A query resolves its structured filters once, then the lexical and vector retrieval stages each build their own filter object to hand to the index, rather than sharing one mutable instance end to end — a fix applied to one path's filter construction does not, by any language guarantee, apply itself to the other's. The ranker merges both candidate sets, attributes every result, and a listing's own text can be scanned for manipulative language without ever being allowed to move its score.

the edgesEvery arrow, spelled out

EdgeWhat movesWhy it is drawn that way
① client → service The query and structured filters, POST /search. No auth, no session, no write route reachable from here — the only write path is the ingestion consumer, below.
② service → client The ranked results, always tagged completed or degraded. C-4: never a silent timeout with no event. A request that produced neither a result nor a recorded reason is a gap someone else has to explain.
filter resolver → retrievers The resolved hard filters — price, city, rooms, AllowedStatuses = [Active]. Each retrieval stage builds its own SearchIndexFilter from this, independently, rather than sharing one mutable object (§2.2) — the seam a hybrid system's asymmetric bugs live in.
retrievers → ISearchIndex QueryAsync (lexical) and VectorQueryAsync (vector), each carrying its own filter. The only interface either path may reach the backend through; normalised so nothing in the spec or a scenario ever names a vendor.
retrievers → hybrid ranker Two candidate sets, merged and attributed to lexical / vector / both. C-5: every result's source and ranking contribution is recorded on the trace — nothing here is a black box a wrong result can hide inside.
ranker → assembler The ranked, attributed list, with any manipulation finding already reported and already ignored. C-7's structural guarantee: the only two numbers that ever feed CombinedScore are a lexical match value and a cosine similarity, both computed the same deterministic way for every listing.
pipeline → OpenTelemetry One span per stage, one span per index call, carrying the filter, the candidate count and the outcome. The trace is the interface between the pipeline and its evals — Layer 1 grades it on every push (ADR-0003).

the write pathOne way in: an ingestion event, applied at most once

There is deliberately no HTTP route that calls IndexAsync or DeleteAsync. The only path to a write is IngestionConsumer, reading listing.published / listing.price_changed / listing.delisted events off a queue, idempotent by event_id — idempotency lives at the consumer boundary, not on a promise that the producer never duplicates.

the measuring loopThe spec came first; the trace is what gets graded

Layer 1 asserts over the trace — which candidates each path returned, how they were filtered and ranked, what was never a candidate at all. It needs no model, no network and no credential, which is why it gates every pull request. Layer 2 is a rubric-anchored judge with five 0–3 anchors and a hashed prompt — pinned, versioned, and never yet run against a live model, because calibration (Cohen's kappa against human labels) has not happened yet (D-1). On a credential-less run it reports skipped:no-credential, never a silent green.

honestlyWhat's real, and what's illustrative

This is a proof of concept, not a deployed service. Exactly one thing in the estate below actually runs anywhere other than a laptop: the GitHub Actions CI workflow. Everything else — local Elasticsearch, Kubernetes manifests — is written down as illustrative, because it has never been applied against a real cluster, and the honest reading belongs on this page, not buried in a code comment.

operationsThere is no deploy — that is the point, for now

A push to a branch never deploys anything, because nothing here deploys at all. This repository is about backend and search-ranking engineering, not showcase infrastructure, so it spends its effort on the pipeline, the contract, and the suite that grades it — and records, in docs/DEVIATIONS.md, exactly which parts of the worked example it mirrors were deliberately not carried over, and why.

What replaces a live environment is the same suite CI runs, runnable by anyone with the .NET 10 SDK and nothing else: dotnet run --project src/ListingSearch.AppHost for the service, dotnet test for everything that grades it.
